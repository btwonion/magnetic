# NeoForge 26.2 Activation Design

## Goal

Activate NeoForge as a second buildable and publishable loader in the existing Stonecutter and ModStitch mod project. Fabric/Quilt remains active, Paper remains unchanged, and both loader variants share gameplay code, mixins, configuration, resources, and committed generated data.

## Version Matrix

The Stonecutter tree will contain these nodes:

- `26.2-fabric`, compiling Minecraft `26.2-pre-4` through Fabric Loom;
- `26.2-neoforge`, compiling Minecraft `26.2` through ModDevGradle.

Fabric remains the VCS-active Stonecutter node. The NeoForge node uses these properties exactly:

```properties
vers.versionName=26.2
vers.mcVersion=26.2
vers.mcVersionRange=>26.1
vers.supportedMcVersions=26.2

vers.deps.fml=26.2.0.10-beta
vers.deps.yacl=3.9.5+26.2-neoforge
vers.deps.klf=3.1

modstitch.platform=moddevgradle
```

## Build and Release Integration

Root settings register `26.2-neoforge` alongside the existing Fabric node. The shared ModStitch build selects ModDevGradle, NeoForge, KotlinLangForge, and NeoForge YACL from the node properties.

`releaseAllPlatforms` depends on both mod release tasks and the existing Paper release task. Root release notifications aggregate and deduplicate supported Minecraft versions from both mod nodes.

The NeoForge metadata template remains generated by ModStitch and declares Minecraft plus loader-required runtime dependencies supported by the supplied properties. ModStitch continues to append mixin configuration and convert `magnetic.classtweaker` into the platform access transformer.

## Loader Source Activation

The existing NeoForge Stonecutter branch becomes compiled source. Its responsibilities remain limited to:

- the `@Mod("magnetic")` entrypoint;
- config-path resolution;
- command registration;
- lazy, idempotent level-tick registration for animation;
- client-only YACL config-screen registration.

Compilation errors caused by NeoForge 26.2 API differences are corrected inside the loader branch. Shared drop logic, mixins, animation calculations, configuration, and Paper code are not redesigned.

## Generated Data

The committed files under `mod/src/main/generated/data/**` are loader-neutral runtime resources. They define the Magnetic enchantment and its four enchantment-tag memberships.

Fabric remains the only data generator in this change. Its existing Fabric datagen providers continue to write `src/main/generated`, which Fabric Loom already adds to resources.

NeoForge does not receive a duplicate `GatherDataEvent` provider implementation. Instead, the NeoForge resource-processing path explicitly includes the shared committed generated-data directory and excludes `.cache/**`. This avoids duplicated generator logic while packaging identical data in both loader artifacts.

Jar inspection is a one-time migration verification step. No permanent artifact-content validation task is added to Gradle.

## Failure Handling

- Missing active-node properties fail Gradle configuration rather than falling back to invented versions.
- Source or loader-API compilation failures are fixed within the NeoForge activation scope.
- If verification fails because Java, Gradle, networking, credentials, or another environment/toolchain prerequisite is misconfigured, report the failure without changing or repairing the environment.
- Publishing tasks are configured but not executed during migration verification.

## Verification

Run:

```bash
./gradlew :mod:26.2-neoforge:build
./gradlew :mod:26.2-fabric:build
./gradlew :paper:build
```

During this migration only, inspect both mod jars and verify they contain:

- `data/magnetic/enchantment/magnetic.json`;
- `data/magnetic/tags/enchantment/auto_move.json`;
- `data/minecraft/tags/enchantment/in_enchanting_table.json`;
- `data/minecraft/tags/enchantment/tradeable.json`;
- `data/minecraft/tags/enchantment/treasure.json`;
- no `.cache/` entries.

NeoForge runtime verification covers dedicated-server initialization, config creation, `/magnetic reload`, item and XP pickup, animated pickup, and client config-screen registration.

## Workspace Preservation

Two pre-existing user changes are outside this implementation and must be preserved without being included in agent commits:

- the staged deletion of `CLAUDE.md`;
- removal of the Nucleoid Maven repository from `mod/build.gradle.kts`.

## Out of Scope

- Restoring or replacing `CLAUDE.md`.
- Reintroducing the Nucleoid Maven repository.
- Changing Paper source, dependencies, metadata, or behavior.
- Porting Fabric datagen providers to NeoForge while the generated output remains loader-neutral.
- Adding a permanent jar-content verification task.
- Publishing artifacts or releases.
